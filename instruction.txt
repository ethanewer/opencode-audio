You must determine whether the eval agent works correctly in all supported settings and whether its prompts and surrounding orchestration produce the intended behavior.

Verify that the eval agent starts in a **new context** when it is supposed to.

### 2. User instruction extraction

Audit the **user instruction extraction agent** carefully.

Verify:

* the user’s instruction is extracted accurately
* it preserves the actual task, constraints, and latest user intent
* it does not over-summarize away important requirements
* it does not introduce new assumptions or distort the task

Also verify invocation timing:

* it should be invoked **only when appropriate**
* specifically, it should be invoked when there are **multiple user messages** or when the **user has answered a question from the model**
* it should not run unnecessarily on simple single-message cases

If the current invocation policy is ambiguous or partially correct, make it explicit, consistent, and well-documented in code and in your report.

### 3. Eval agent behavior and permissions

Verify that the eval agent is prompted and configured to behave correctly.

It should:

* actively investigate problems
* run tests when useful
* write temporary scripts or test harnesses when useful
* gather enough evidence to support its conclusions

It must **not modify repository files**.

Check both prompt wording and actual enforcement. If “should not modify files” is only implied and not reliably enforced, fix that.

### 4. Eval output quality and format

This is extremely important.

Audit whether the feedback produced by the eval agent is in a format that is actually useful for the downstream build agent.

The eval output must:

* clearly explain the issue or issues found
* include enough detail for the build agent to act
* distinguish verified problems from suspicions
* provide clear next-step instructions
* avoid ambiguity, vagueness, or bloated commentary
* make it easy for the build agent to either:

  1. fix the issues, or
  2. call the **eval rebuttal tool** to challenge the evaluation

You must verify that the format is strong not just in theory, but in real examples across the supported flows.

### 5. Build-agent handoff

The build agent must receive eval feedback in a form it can reliably use.

Audit whether the handoff from eval to build is working correctly:

* Does build understand the eval output?
* Does build attempt to fix the issues directly when appropriate?
* Does build invoke the **eval rebuttal tool** when it disagrees?
* Are there cases where build gets stuck because eval output is poorly structured or insufficiently actionable?

Fix prompt design and orchestration issues so that this handoff is reliable.

### 6. Eval rebuttal flow

Verify that the **eval rebuttal** path works correctly end to end.

Specifically test whether:

* rebuttal is available in the right circumstances
* build can use it correctly
* the triggering conditions are sensible
* the system behaves well when eval is wrong, incomplete, or overly strict

If the rebuttal flow is missing, weakly prompted, or poorly integrated, fix it.

Audit all prompts related to:

# Guidelines on prompt improvement

Use these guidelines when improving prompts for engineering agents, audits, or agent-behavior investigations.

## 1. Define the objective clearly

State exactly what success looks like. Replace vague goals like “look into this” with concrete outcomes like:

* audit all entrypoints
* fix issues found
* verify with tests
* document results
* publish the branch

## 2. Separate scope from requirements

Make it easy to see:

* where the agent must look
* what behaviors it must verify
* what fixes it is expected to make

This prevents omissions and reduces misinterpretation.

## 3. Convert paragraphs into executable checks

Long prose often hides important requirements. Turn them into explicit audit items such as:

* verify eval starts in a new context
* verify instruction extraction runs only under defined conditions
* verify eval can run tests but cannot modify files

This makes the prompt more actionable.

## 4. Distinguish “investigate” from “fix”

If you want the agent to do more than inspect, say so explicitly. Good prompts clearly state:

* what must be audited
* what must be changed if broken
* what should be left alone if already correct

## 5. Define behavior, not just implementation details

Say what the system should do from a product and UX perspective, not only which code paths to inspect. This helps the agent catch problems that are technically consistent but still wrong in practice.

## 6. Call out critical quality bars

If one part matters more than the rest, label it clearly. For example:

* “This is extremely important”
* “The output must be actionable for the build agent”
* “Do not treat format quality as a minor detail”

This helps the agent prioritize correctly.

## 7. Specify trigger conditions precisely

Where timing matters, define when something should and should not happen. Ambiguous phrases like “when needed” should be replaced by rules such as:

* only when there are multiple user messages
* only after the user answers a model question

## 8. Require end-to-end verification

Do not rely only on code inspection. For workflow features, require testing through the real entrypoints and loops where behavior may differ.

## 9. Require documentation of both correct and incorrect behavior

A strong audit prompt should ask the agent to document:

* what is already correct
* what is broken
* how it knows
* what changed

This produces a more trustworthy final report.

## 10. Encourage initiative on adjacent issues

If the prompt is too narrow, the agent may ignore obvious related problems. Add a clause allowing fixes for nearby issues that are clearly part of the same feature area.

## 11. Tighten ambiguous terms

Replace fuzzy language like:

* “works correctly”
* “good format”
* “right times”

with definitions such as:

* starts in a clean context
* produces actionable, structured feedback
* only invokes extraction under specified conditions

## 12. Make deliverables explicit

Always state the required outputs:

* code changes
* tests
* markdown report
* branch name
* commit hash

Without this, agents often stop after partial completion.
