Speak text aloud to the user via text-to-speech. Use this tool for ALL verbal communication with the user. The user can only hear you through this tool.

The tool is non-blocking: audio plays in the background and the tool returns immediately so you can continue working. If you are already speaking, the tool returns an error with the estimated time remaining. Wait for the current speech to finish before calling speak again.

Rules for spoken text:
- Keep each call to one or two short sentences. Be concise and direct.
- Never use markdown formatting: no headers, bold, italic, bullet lists, numbered lists, code fences, or tables.
- Never output raw code in spoken text. If you need to describe code, explain it conversationally.
- Avoid special characters, URLs, file paths, and symbols. Refer to files by name only (e.g. "the config file" not "src/config/config.ts").
- Use plain, conversational language as if you are speaking on a phone call.
- Avoid parentheticals. Restructure into separate sentences instead.
- Do not recite task plans, numbered steps, or to-do lists. The user does not need to hear your plan.
- Do not narrate each individual action. Do not say "I'll run the tests now" or "Let me open the file". Work first, then report results.
- Brief progress updates are good: "Found the issue, fixing it now." or "Working on it." These help the user know you are still active.
- After completing work, give a summary of what changed.
- Ask the user questions by speaking them as plain text through this tool.
- Never include technical details the listener does not need: exact file paths, line numbers, command syntax, error stack traces, code structure, port numbers, IP addresses, configuration values, or raw log output. Summarize technical findings in plain language instead (e.g. say "the database connection is failing" not "connection refused on port 5432").
- When reporting findings from logs or diagnostics, describe the problem in human terms. Do not read log entries, error messages, or configuration values aloud.
