The todowrite tool is your structured planning, scratchpad, and progress-tracking channel. Use it to externalize your plan, hypothesis, and observations so your later turns can read them back and stay oriented.

On any non-trivial task you should build a todo list. You do not have to call todowrite on your very first turn — it is fine to use read-only tools first (read, ls, cat, grep, file, etc.) to gather enough context to plan. But as soon as you are about to take a side-effect action (write, edit, apply_patch, or a side-effect shell command like installs, builds, running scripts, mkdir, rm, package managers, etc.), you must first have an active \`in_progress\` todo with populated \`notes\`. The runtime enforces this: side-effect tool calls are blocked until the todo list is in the right state.

## The three fields per todo

Every todo has THREE fields. All three are required. The \`notes\` field is where you think.

- \`content\` — a short imperative title, one line (e.g. "Parse the ELF program headers"). Do not put analysis here.
- \`status\` — one of \`pending\`, \`in_progress\`, \`completed\`, \`cancelled\`. Exactly one item may be \`in_progress\` at a time.
- \`notes\` — your working notes for this todo. Always populate this. This is where your plan, hypothesis, and observations live. See the notes guide below.

## How to write the \`notes\` field

Notes are your working prose: plan, hypothesis, observation. Your own notes are what you will read next turn to stay oriented.

- While a todo is \`pending\`: 1–3 sentences sketching what you plan to do and why. A quick hypothesis is fine.
- When you flip a todo to \`in_progress\`: expand the notes to 2–5 sentences covering:
  - Your current hypothesis about the problem
  - The specific commands or edits you are about to run
  - What outcome you expect (and how you will know if the result is wrong)
- When you mark a todo \`completed\`: replace the notes with 1–3 sentences describing what you actually did, what you observed, and any new facts that affect later todos.
- When you mark a todo \`cancelled\`: one sentence saying why it is no longer needed.

Never leave \`notes\` empty. Never write \`notes: "TBD"\` or \`notes: "see plan"\`. Write the actual thought.

## The recommended workflow

1. **Optional read-only exploration.** If the task is ambiguous or you need structural context, run a small number of read-only commands first (read, ls, cat, grep, file). These do not require a todo list.
2. **Build the plan.** As soon as you have a picture of the task, call todowrite with 3–8 todos covering the milestones you plan to hit. Set the first one you will work on to \`in_progress\` and populate its \`notes\` with your immediate plan.
3. **Before each chunk of side-effect work.** Re-enter the \`in_progress\` todo's \`notes\` with: your current hypothesis, the specific commands/edits you are about to run, and what outcome you expect. Then run those tool calls.
4. **After a chunk of work.** Update the \`notes\` with what you actually observed. If the todo is done, mark \`completed\` and summarise. If the plan changed, add/re-word/cancel todos.
5. **Before task_complete.** Every todo must be \`completed\` or \`cancelled\`. Bounced calls will resume the loop until every todo is resolved.

Only ONE todo may be \`in_progress\` at any given moment. Do not mark a todo \`completed\` until it is actually done — do not batch completions across multiple unrelated items in a single update.

## Example — good usage on a multi-step task

<example>
User: Build ccomp (CompCert 3.13.1) from source and make it available at /tmp/CompCert/ccomp.

Optional first turn: a couple of read-only probes (uname -a, which ocaml) — no todo yet.

Next turn: the first todowrite, before any install command:
todowrite({todos: [
  {content: "Install OCaml, Coq 8.15+, and menhir via opam", status: "in_progress", notes: "apt coq is 8.12, too old for CompCert 3.13.1. Plan: apt-get install opam -y, opam init --disable-sandboxing --yes, opam install coq.8.17.1 menhir ocaml --yes. Expect ~10 minutes of compilation. If opam init fails on sandboxing, fall back to --unsafe-yes."},
  {content: "Download CompCert 3.13.1 source", status: "pending", notes: "Fetch https://compcert.org/release/compcert-3.13.1.tgz into /tmp/CompCert, verify the tarball unpacks and contains a configure script."},
  {content: "Configure and build", status: "pending", notes: "Run ./configure x86_64-linux then make -j$(nproc). Expected artifact: ./ccomp binary in the build tree."},
  {content: "Install to /tmp/CompCert/ccomp and verify", status: "pending", notes: "Copy or symlink ccomp into /tmp/CompCert/ccomp. Verify with /tmp/CompCert/ccomp -v and a hello-world compile."}
]})

After the install finishes:
todowrite({todos: [
  {content: "Install OCaml, Coq 8.15+, and menhir via opam", status: "completed", notes: "opam init + opam install coq.8.17.1 menhir succeeded. coqc --version reports 8.17.1. ocaml is 4.14. Ready to download CompCert."},
  {content: "Download CompCert 3.13.1 source", status: "in_progress", notes: "About to curl the release tarball into /tmp/src and tar xzf it. Expect a directory /tmp/src/CompCert-3.13.1 with ./configure."},
  ...
]})
</example>

## Example — when todos are not required

<example>
User: Add a comment to the calculateTotal function.

This is a single-step change. You may edit the file directly without a todo list. The gate only engages on multi-step tasks where you actually plan to take side-effect actions beyond a trivial one-shot edit.

Note: on terminal-bench tasks, which almost always require multiple shell commands and edits, you will almost always need a todo list.
</example>

Resolve every todo to \`completed\` or \`cancelled\` before calling task_complete.
